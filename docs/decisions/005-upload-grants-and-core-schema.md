# 005. 업로드 발급 기록과 공통 스키마 연결

S-03의 업로드 발급 계약(bucket/path/token)과 경로(owner/purpose/uuid.ext)를 유지한다. 발급 시 레시피 소유권을 확인하고 upload_grants에 소유자·대상 레시피·용도·선언 크기·형식을 저장한다. 기록 저장에 실패하면 토큰을 응답하지 않는다. 레시피 ID와 소유자 ID의 복합 외래 키로 발급 기록의 소유 관계를 DB에서도 보장한다. 채팅 이미지는 본인 소유 초안에만 발급하며, STT 최초 업로드는 기존대로 레시피 ID 없이 허용한다. 저장소 객체의 덮어쓰기 토큰은 발급하지 않는다.

경로 접두사만 검사하는 대안은 같은 사람의 다른 레시피나 다른 용도로 발급한 파일을 구별하지 못한다. 발급 기록을 추가하면 DB 조회 한 번이 늘지만 대상·용도까지 검증할 수 있다. 채팅에서는 발급 기록의 사용자·레시피·버킷·용도와 실제 객체의 크기·형식을 모두 확인한 뒤 읽기용 서명 URL을 만든다. 기존에 기록 없이 발급한 경로는 허용하지 않으며 다시 업로드해야 한다.

기록은 업로드 토큰이 아니라 발급 근거이므로 토큰 만료 후에도 보존한다. 오래된 채팅의 이미지를 다시 읽을 수 있어야 한다. 토큰 자체를 DB에 저장하지 않는다. 일반 클라이언트는 이 테이블에 접근할 수 없고 서버만 조회·추가한다.

채팅 브랜치에는 기본 테이블 마이그레이션이 없어 현재 추가 마이그레이션만으로 빈 DB를 구성할 수 없다. profiles는 온보딩 브랜치의 role 없는 스키마를 그대로 사용하고, 나머지 기본 테이블은 홈 피드 브랜치의 초기 DDL에서 분리한다. 다른 브랜치 전체를 병합하는 대안은 무관한 API와 작업 이력을 함께 가져온다. 필요한 공통 DDL만 연결해 이 브랜치의 마이그레이션 순서를 검증한다. 이후 홈 피드의 기존 0001_init.sql을 통합할 때는 같은 테이블을 두 번 만들지 않도록 마이그레이션 이력을 정리해야 한다. 이미 배포된 DB의 이력은 이 작업에서 변경하지 않는다.

원격 마이그레이션과 외부 모델 호출은 별도 실행 단계다. 환경변수와 Supabase 실행 환경이 없으면 로컬 SQL·서비스·HTTP 검증 결과와 미실행 범위를 구분해 보고한다.
