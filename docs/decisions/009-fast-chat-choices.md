# 009. 채팅 선택지와 전체 분석 분리

## 배경

채팅 완료 후 클라이언트와 서버가 각각 전체 레시피 분석을 호출한다. 선택지 표시가 전체 분석 응답에 묶여 있다. 이 결정은 #83의 채팅 이후 흐름을 다룬다.

## 결정

채팅은 짧은 요청으로 다음 질문 하나와 선택지 2~4개를 만든다. 서버는 질문을 assistant 메시지에 저장하고 `choices` SSE 이벤트로 보낸다. 선택한 값이나 직접 입력은 기존 사용자 메시지로 저장된다. 전체 분석은 저장된 대화에서 질문과 답변을 읽고, 성공한 채팅 요청마다 기존 백그라운드 작업에서 한 번 시작한다. 클라이언트는 채팅 완료 후 전체 분석을 다시 호출하지 않는다.

클라이언트는 빠른 질문을 현재 채팅 턴에 고정한다. 늦게 끝난 전체 분석은 저장 검증에 사용되며 표시 중인 질문을 교체하지 않는다. 분석은 자신의 턴이 이미 지난 경우 모델을 호출하지 않는다. 기존 DB의 마지막 메시지 검증은 실행 중 새 턴이 생겨도 오래된 분석이 최신 답변을 덮지 않도록 한다. 감각 답변은 실제로 표시한 질문을 기준으로 평가한다. 발행 검증은 서버가 맡는다.

이벤트는 추가 방식이다. 빠른 선택지 생성이 실패하거나 질문이 없으면 null을 보낸다. 기존 서버가 이벤트를 생략해도 새 클라이언트는 직접 입력과 명시적인 분석을 사용할 수 있다.

## 대안

전체 분석만 최적화하는 방식은 분석 생성 시간과 스키마 재시도를 화면에서 계속 기다리게 한다. 별도 선택지 API는 채팅과 별도로 질문과 메시지를 연결해야 한다. SSE로 같은 턴에 전달하면 기존 채팅 저장 흐름을 재사용할 수 있다.

## 결과

초기 녹음 직후의 분석과 발행 조건은 기존 경로를 사용한다. 짧은 요청이 추가되므로 비용과 지연은 배포 환경에서 별도로 측정한다.
